# UC19 — Interpretação textual

Implementação interna em `src/modules/ai_processing`, com persistência pertencente
ao Journal e consulta de temas pelo Catalog. Não exige migração: utiliza `analysis`
e `journal_entries`, já existentes, com IDs ULID do backend.

## Uso interno

```python
from src.modules.ai_processing.bootstrap.use_cases import get_interpret_entry

# Usa o adaptador OpenAI configurado no ambiente.
use_case = get_interpret_entry()
analysis_id = await use_case.execute(entry_id, owner_id)
```

O chamador deve obter `owner_id` da identidade autenticada ou de um evento interno
confiável, nunca do corpo de uma requisição sem autorização. A leitura e a gravação
filtram a entrada pelo proprietário e excluem entradas apagadas.

Sem chave ou modelo configurado, o adaptador lança `ProviderNotConfiguredError`;
nenhum resultado fictício é produzido e nenhum estado é alterado. O bootstrap é usado pelo worker de análise descrito abaixo. A criação permanece
em rascunho; o envio explícito coloca a entrada na fila persistida no PostgreSQL.

## Contrato provisório independente do provedor

O adaptador recebe `InterpretationRequest`: texto, contexto, temas ativos e
instruções de interpretação. Deve transmitir as instruções como instruções do
sistema e o texto/contexto como dados, exigir saída estruturada e retornar um
dicionário no formato abaixo:

```json
{
  "summary": "Resumo da reflexão",
  "main_message": "Interpretação central sem diagnóstico",
  "themes": [{"theme_id": "ID_EXISTENTE_NO_NEO4J", "confidence": 0.8}],
  "sentiments": ["preocupação"],
  "tone": "reflexivo"
}
```

Não há criação automática de temas. IDs desconhecidos, inativos ou duplicados são
rejeitados. A elegibilidade dos temas selecionados é consultada novamente antes de
salvar. Catálogo vazio ou ausência de associação permite `themes: []`.
O catálogo e o PostgreSQL não compartilham transação distribuída; uma alteração
posterior à última consulta não é bloqueada. O resultado guarda o snapshot dos temas.

`summary` e `main_message` são persistidos nas colunas correspondentes;
temas, sentimentos, tom e `schema_version` ficam em `content_meta`. Temas recebidos
da IA ficam com `source=ai` e `confirmed_by_user=false`.
O resultado não é vinculado artificialmente a sentenças: extração de sentenças,
embeddings, referências e recomendações não fazem parte deste núcleo.

Limites iniciais: texto até 10.000 caracteres, até 100 temas selecionados, até 20
sentimentos e timeout de 30 segundos (configurável no construtor). Ajustar os
limites e o orçamento de tokens quando o modelo for escolhido.

A chamada externa ocorre fora de transações. Ao salvar, uma trava na entrada e
a comparação do snapshot recusam resultados de entradas alteradas, apagadas ou
já analisadas. Resultado e estado `analyzed` são confirmados na mesma transação.
Falhas não sobrescrevem análises anteriores nem alteram os estados atuais.
O worker marca falhas como `analysis_failed` sem retries automáticos.
Eventos e rastreabilidade operacional ampliada continuam no UC25 (#17).
A consulta da análise pelo usuário pertence ao UC02 (#18).

## Configuração OpenAI

Provedor definido: OpenAI, usando `POST /v1/responses` via HTTPX já instalado.
O adaptador usa Structured Outputs com o schema de `Interpretation`, separa as
instruções do texto/contexto e envia `store=false`. Recusas, respostas incompletas,
erros HTTP e saída inválida são rejeitados com erro sanitizado.

Copie `.env.ai.example` para `.env.ai.local` no diretório `Codigo/BACK` e configure
`OPENAI_API_KEY` e `OPENAI_MODEL`. O arquivo local está ignorado pelo Git.
O adaptador também lê `.env.dev` (ou `.env.test`/`.env.prod` conforme `ENV`),
com caminhos relativos ao backend, independentemente do diretório do terminal.
`.env.ai.local` sobrescreve o arquivo do ambiente; variáveis do processo têm
precedência sobre ambos. `.env.dev` é versionado: não envie credenciais ao Git. Use uma nova chave caso a anterior tenha sido exposta.

O modelo deve estar habilitado no projeto e suportar Structured Outputs.
`OPENAI_TIMEOUT_SECONDS` (30) e `OPENAI_MAX_OUTPUT_TOKENS` (2000) são configuráveis.
`gpt-5-nano` usa `reasoning.effort=minimal` por padrão para reservar o orçamento
para o JSON final. `OPENAI_REASONING_EFFORT` permite sobrescrever conforme o modelo.
Não há retries automáticos neste adaptador; a política de orquestração ainda deve
ser definida. A chamada à OpenAI é executada pelo worker, fora da requisição HTTP.

Referência: https://developers.openai.com/api/docs/guides/structured-outputs

## Diário e worker (integração inicial UC24)

1. Crie a entrada com `POST /journal/entries`, autenticado, ou pela interface.
2. Envie `POST /journal/entries/{id}/analysis` com a mesma autenticação.
   Retorna 202 e `pending_analysis`. O proprietário vem da sessão autenticada.
   Rascunhos e entradas com falha podem ser enviados; pendentes são idempotentes.
3. Execute o worker no diretório `Codigo/BACK`:

```bash
DEBUG=false NEO4J_URI=bolt://localhost:7687 .venv/bin/python -m src.modules.ai_processing.worker
```

Para processar somente uma entrada pendente e encerrar:

```bash
DEBUG=false NEO4J_URI=bolt://localhost:7687 .venv/bin/python -m src.modules.ai_processing.worker --once --entry-id ID_DA_ENTRADA
```

Os overrides são para execução no terminal local: o `.env.dev` contém endereço
Neo4j da rede Docker; alguns terminais exportam `DEBUG=release`, inválido para
as configurações da aplicação. Em Docker, use:

```bash
docker compose -f docker-compose.api_workers.yml --profile ai up -d --build worker_journal_analysis
```

O worker consulta uma entrada pendente a cada cinco segundos. Não processa
rascunhos, apagados, analisados ou falhas sem novo envio explícito. Uma trava
consultiva de sessão PostgreSQL serializa os workers, sem manter uma transação
aberta durante a chamada externa. O resultado é salvo em `journal_schema.analysis`
com status `completed`, e a entrada muda para `analyzed` na mesma transação.
Falhas ficam em `analysis_failed`; logs incluem IDs e classe do erro, nunca texto
ou credenciais. Uma queda depois da resposta da API e antes do commit pode gerar
nova chamada paga na retomada; a gravação continua protegida contra duplicação.

Teste completo com um usuário já existente (cria uma entrada real fictícia e
consome créditos):

```bash
DEBUG=false NEO4J_URI=bolt://localhost:7687 .venv/bin/python -m src.modules.ai_processing.demo_journal --user-id ID_DO_USUARIO
```

Ao terminar, o comando consulta o banco e imprime o estado e a análise persistida.
A página da reflexão oferece Solicitar análise de IA e Ver análise.
O GET autenticado `/journal/entries/{id}/analysis` retorna estado e resultado
(ou `analysis: null` enquanto não existe). A tela consulta a cada cinco segundos
enquanto pendente e oferece novo envio após falha. Rascunhos continuam editáveis
até o envio explícito; o worker precisa estar executando para consumir a fila. Nenhuma migração nova é necessária.
